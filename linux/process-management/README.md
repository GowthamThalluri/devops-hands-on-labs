# Linux Process Management — Hands-On Practice

## 1. Overview

A process is a running instance of a program. Linux assigns each process a Process ID (PID), and most processes have a Parent Process ID (PPID).

Process management helps DevOps engineers investigate resource usage, identify application processes, understand process relationships, and manage background tasks safely.

All exercises in this document were performed in Ubuntu on WSL using temporary practice processes where appropriate.

## 2. Inspect Resource Usage with `ps`

### Command

```bash
ps -eo pid,ppid,stat,%cpu,%mem,comm --sort=-%cpu | head -n 8
```

### Purpose

- `ps -eo`: Selects the process fields to display.
- `pid`: Process ID.
- `ppid`: Parent Process ID.
- `stat`: Process state and flags.
- `%cpu`: Reported CPU usage.
- `%mem`: Percentage of memory used.
- `comm`: Command name.
- `--sort=-%cpu`: Sorts by CPU usage in descending order.
- `head -n 8`: Displays the first eight lines, including the header.

### Observation

The initial output showed low reported CPU and memory usage for the listed processes.

A single snapshot is not enough to diagnose a performance problem. Observe the system over time and correlate CPU, memory, I/O, and application symptoms.

## 3. Inspect the Process Tree

### Command

```bash
ps -ef --forest | head -n 20
```

### Purpose

Displays detailed process information with a tree-style representation of parent-child relationships.

Important fields:

- `UID`: User running the process.
- `PID`: Process ID.
- `PPID`: Parent Process ID.
- `C`: Scheduling-related CPU usage field.
- `STIME`: Process start time.
- `TTY`: Associated terminal, if any.
- `TIME`: Accumulated CPU time.
- `CMD`: Command line.

### Observation

The output showed the Bash shell and its child commands. It also showed a parent-child chain involving the `chronyd` time-synchronization service.

**Key insight:** Multiple related processes do not automatically indicate a problem. Identify each process and inspect its relationships before taking action.

## 4. Monitor Processes with `top`

### Command

```bash
top
```

### Purpose

Displays a continuously refreshing view of system activity, including CPU, memory, tasks, and individual processes.

Useful fields:

| Field | Meaning |
|---|---|
| PID | Process ID |
| USER | User running the process |
| PR | Scheduler priority reported by `top` |
| NI | Niceness value |
| VIRT | Virtual memory size |
| RES | Resident memory |
| S | Process state |
| %CPU | CPU usage |
| %MEM | Percentage of memory used |
| COMMAND | Process command |

Press `q` to exit.

### Observation

The WSL environment showed approximately 100% CPU idle time, 24 tasks, no zombies, and about 3.3 GiB of available memory.

These figures describe that particular snapshot, not the system's permanent performance.

An idle CPU does not mean no processes are running.

## 5. Find Processes with `pgrep`

### Command

```bash
pgrep -a chronyd
```

### Purpose

Finds processes matching the specified process-name pattern and displays matching PIDs and command lines.

### Observation

The command returned entries associated with the `chronyd` time service, including a starter script and `chronyd` processes.

Always verify a process's identity and role before terminating it. A matching name alone does not establish that the process is unnecessary or duplicated incorrectly.

## 6. Run a Process in the Background

### Command

```bash
sleep 300 &
```

### Purpose

- `sleep 300` waits for 300 seconds.
- `&` starts the command as a background job.

Bash returned a job number and PID.

Inspect shell jobs with:

```bash
jobs -l
```

The job number is used with shell job-control commands; the PID identifies the Linux process.

## 7. Stop a Process with `kill`

### Command

```bash
kill %1
```

### Purpose

Sends the default `SIGTERM` signal to job number 1 in the current shell.

For a known PID, use:

```bash
kill PID
```

Replace `PID` with the actual process ID.

`SIGTERM` requests graceful termination. If a process finishes before the command runs, Bash may report that the PID no longer exists.

### Signal distinction

- `SIGTERM`: Requests graceful termination.
- `SIGINT`: Commonly generated by Ctrl + C to interrupt the foreground process.
- `SIGTSTP`: Commonly generated by Ctrl + Z to suspend the foreground process.
- `SIGKILL`: Forces termination and cannot be caught or ignored by the target process.

Prefer graceful termination first. Use forced termination only when necessary.

## 8. Suspend and Resume Jobs

### Start a foreground process

```bash
sleep 300
```

Press `Ctrl + Z` to suspend it.

### Check jobs

```bash
jobs -l
```

### Resume in the background

```bash
bg %1
```

### Bring the job into the foreground

```bash
fg %1
```

Press `Ctrl + C` to interrupt the foreground test process.

### Key distinction

- `Ctrl + Z` suspends the foreground job.
- `bg` resumes a suspended job in the background.
- `fg` brings a job to the foreground.
- `Ctrl + C` sends an interrupt signal to the foreground process group.

These operations control jobs associated with the current shell.

## 9. Set Process Niceness with `nice`

### Command

```bash
nice -n 10 sleep 300 &
```

### Purpose

Starts a process with a niceness value of 10.

A higher niceness value generally means lower CPU scheduling priority for a normal process.

Inspect the result:

```bash
ps -o pid,ni,pri,cmd -p PID
```

Replace `PID` with the actual process ID.

The `NI` column displays the niceness value. Do not treat the displayed `PRI` value as the niceness value; scheduler priority is represented separately.

## 10. Change Niceness with `renice`

### Command

```bash
renice 10 -p PID
```

Replace `PID` with the actual process ID.

### Purpose

Changes the niceness of an existing process without restarting it.

During practice, the temporary `sleep` process changed from niceness `0` to `10`.

For normal processes, increasing niceness generally reduces CPU scheduling priority. Permissions determine which niceness changes a user may make.

## 11. Run a Command with `nohup`

### Command

```bash
nohup sleep 600 > /tmp/nohup-process-lab.log 2>&1 &
```

### Purpose

- `nohup`: Makes the command ignore hangup signals.
- `sleep 600`: Creates a temporary process.
- `>`: Redirects standard output to a file.
- `2>&1`: Redirects standard error to the same destination.
- `&`: Starts the command in the background.

Verify the process:

```bash
ps -p PID -o pid,ppid,stat,cmd
```

Inspect the log:

```bash
cat /tmp/nohup-process-lab.log
```

The log was empty because `sleep` does not normally print output.

The process was terminated with `kill`, and verification confirmed that it had ended.

**Important:** `nohup` is a basic tool for simple long-running commands. It is not a replacement for a service manager. Production workloads are generally better managed with tools such as systemd or an appropriate job scheduler.

## 12. Safe Troubleshooting Workflow

When investigating a slow or failing application:

1. Inspect processes with `ps`.
2. Monitor live resource usage with `top`.
3. Find relevant processes with `pgrep`.
4. Trace process relationships when needed.
5. Identify the exact PID before sending a signal.
6. Prefer graceful termination over forced termination.
7. Use `nice` or `renice` only when adjusting scheduling priority is appropriate.
8. Verify the outcome after every process-management action.

Never terminate an unfamiliar production process simply because its name looks suspicious.

## 13. Key Takeaways

- PID identifies a process; PPID identifies its parent.
- Process inspection commands provide snapshots, not a complete diagnosis.
- CPU idle time does not mean that no processes are running.
- `jobs`, `bg`, and `fg` manage shell jobs.
- `kill` sends signals to processes or shell jobs.
- `nice` sets niceness at process startup; `renice` changes it later.
- `nohup` changes hangup-signal handling but is not a full process supervisor.
- Verify process identity before changing or stopping it.
